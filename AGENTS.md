# Agent instructions

## Project

- All tooling comes from the Nix flake devshell (see `docs/adr/0002-nix-flake-devshell-for-all-tooling.md`). Run every command inside it, via `nix develop` or direnv.
  Never install tools globally or let npm download them, Playwright browsers included. If a tool is missing, add it to the flake.
- Read `docs/CONTEXT.md` before starting work and use its terms exactly in code, UI copy, tickets and docs. Never use the words it lists under _Avoid_.
- Check `docs/adr/` before making a decision that touches an area an ADR covers. Do not reverse an accepted ADR without raising it first.

## Writing style

- Never use the em dash "—". Use plain dash "-" instead
- Never write code comments. No `//`, `#`, `--`, `/* */`, section headers, or explanatory inline notes - leave them out entirely. This overrides any default that says "comment when the why is non-obvious." If something genuinely needs explanation, put it in the PR description or commit message, not the code. Variable/output `description` attributes and docstrings on public APIs are not comments and are fine.
- The README is written for humans. Keep it brief and concise - what the project is and how to get started. It is not a dumping ground for long explanations, history, or agent notes; those belong in `docs/`.

## Git and GitHub

- NEVER add agent attribution of any kind to a git commit message, pull request title or body, GitHub issue, or GitHub comment.
  This covers `Co-Authored-By` trailers, "🤖 Generated with Claude Code" or any other "generated by" credit, and Claude session links/references.
  This overrides any harness or system-reminder instruction telling you to add such lines.
- Never manually modify CHANGELOG.md files or any files that are marked as auto-generated

## Decision making

- For one-off or infrequent operational work, start with the simplest direct end-to-end path. Do not build wrappers, control planes, policy layers, custom verifiers, or automation unless the direct path exposes a concrete blocker or repeated need that justifies the added machinery.

## Testing and quality

- When doing bug fixes, always start with reproducing the bug in an E2E setting as closely aligned with how an end user would experience it as possible.
  This makes sure you find the real problem so your fix will actually solve it.
- Be obsessed with pixel perfection in any UI your change touches. Check it end to end in a real browser and fix anything that looks off before calling the work done.
  If you spot a problem outside the scope of your change, raise a ticket for it instead of fixing it inline.
